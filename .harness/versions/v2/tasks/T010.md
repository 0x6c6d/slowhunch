# T010: PDF intake via pdf.command

Phase 3 · Model: opus: runs a configured external program on owner files (A1, Risk: PDF subprocess) · Depends-on: T001 T009 · Covers: R31, R7, R22

## Brief
Make `slowhunch add file.pdf` extract plain text by running `pdf.command` from config.

- `internal/intake/read.go`: add `type ReadOptions struct { PDFCommand []string; PDFTimeout time.Duration }`
  and `ReadWith(arg string, stdin io.Reader, o ReadOptions) (Input, error)`; `Read(arg, stdin)` stays and
  equals `ReadWith` with empty options (then `.pdf` stays `UNSUPPORTED`, as in v1).
- For an existing file whose extension is `.pdf` and a non-empty `PDFCommand`: build argv by copying
  `PDFCommand` and replacing every element that is exactly `{file}` with the cleaned absolute path of the
  file (an element merely containing `{file}` is left unchanged); run it with
  `execprov.RunArgv(ctx, argv, nil, nil, timeout, 1<<20)` (timeout default 60 s, PATH-only env, no shell);
  stdout is the text. Then apply the normal checks: valid UTF-8, the 12,000-character cap (`TOO_LONG`),
  non-empty after trimming. Result `Input{Text: <stdout>, Path: arg, Ext: ".pdf"}`; `InferMedium` returns
  `article` for `.pdf`.
- Missing program, non-zero exit, timeout, output over the cap, or empty/whitespace output ->
  `errs.New(errs.Unsupported, "<what went wrong>", "install pdftotext or set pdf.command")`. No OCR, no
  fallback, the PDF bytes are never copied into the vault: the extracted text is stored as the inbox text
  (`inbox/<source-id>.txt`) exactly like a `.txt` input. Other binary extensions stay `UNSUPPORTED` as in v1.
- `internal/pipeline/add.go`: `Options` gains `PDFCommand []string`; `Add` calls `intake.ReadWith`. The cli
  `add` passes `cfg.PDF.Command`. Secret detection, normalization and hashing run on the extracted text.
- Adapt the three v1 tests that expect `.pdf` to be `UNSUPPORTED` (`internal/intake/read_test.go`,
  `internal/cli/cmd_add_test.go`, `internal/pipeline/add_test.go`): keep the assertion for plain `Read` and
  for a config whose `pdf.command` names a program that does not exist; never depend on whether
  `pdftotext` is installed.

Tests (helper = the test binary re-exec'd with a marker argument, configured as `pdf.command`):
`TestPDFExtract` in `internal/intake`: text returned, `{file}` substituted as a whole element only, helper
sees only `PATH` in its environment (assert a planted `SLOWHUNCH_LEAK` is absent), a shell metacharacter in
the file name arrives literally. `TestPDFUnsupported` in `internal/intake`: missing program, exit 1, empty
output, output over 12,000 characters (`TOO_LONG`) each fail with the right code and the hint text.
`TestPDFAdd` in `internal/cli`: `add paper.pdf --title T --author A` with the helper writes a source with
`medium: article`, an `inbox/<id>.txt` holding the helper's text, and no `.pdf` file in the vault.

## Verification
`.harness/verify/v2/T010.sh` exits 0. It runs `TestPDFExtract`, `TestPDFUnsupported`, `TestPDFAdd` and the
intake, pipeline and cli packages; with the built binary (negative) `add x.pdf` under a `pdf.command` that
does not exist fails `UNSUPPORTED` with the hint and writes nothing, and a `pdf.command` of `false` fails the
same way.
