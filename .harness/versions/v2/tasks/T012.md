# T012: Wildcard lane

Phase 3 · Model: opus: changes which gate-rejected items are written (add orchestration) · Depends-on: T011 · Covers: R28, R12 (wildcards)

## Brief
Implement the wildcard lane in `internal/pipeline` (single `add` and batch `add --from`) and the report
type in `internal/report/report.go`.

- `report.Wildcard{Item string; Reason string; Kept bool}` with JSON `{item, reason, kept}`;
  `Report.Wildcards` becomes `[]Wildcard` (still `[]` when empty). `item` is the source id for a single add
  and `line <n>: <file>` for a batch entry; `reason` is the gate's reason.
- Every gate-rejected item of a run is listed in `wildcards`, never dropped silently.
- Pool = all gate-rejected items of the run (a batch is one run). Keep `k = floor(place.wildcard_share *
  len(pool))` of them: sort the pool by `sha256(text_hash)` hex ascending, ties by entry index, take the
  first k. A single rejected item is therefore never kept (k = 0 at the default 0.10).
- Kept wildcards continue through extract, place and write like gate-accepted items; every atom they
  produce gets the tag `wildcard` (added to `tags`, no duplicates) and the entry's `kept` is true.
- Batch entry reports: a rejected entry's own report lists itself in `wildcards`; the batch result's
  `counts` gains `wildcards` (rejected) and `wildcards_kept`.

Tests `TestWildcardTen` (pipeline or cli, fake provider): a batch of 10 entries all rejected by the gate
writes exactly one entry, whose atoms carry tag `wildcard`, and the chosen one is the lowest
sha256(text_hash); all 10 appear in `wildcards` with exactly one `kept: true`. `TestWildcardSingle`: a
single rejected `add` writes nothing and lists the item with `kept: false`. `TestWildcardShare`: share 0.5
with 4 rejected keeps 2; share 0 keeps none. Adapt v1 tests that asserted `wildcards` is always `[]`.

## Verification
