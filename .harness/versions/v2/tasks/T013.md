# T013: Per-medium cap runs_per_day

Phase 3 · Model: sonnet: state counter plus a pre-send check with clear tests · Depends-on: T002 T011 · Covers: R33, R23

## Brief
Implement `caps.by_medium.<medium>.runs_per_day` for `add` runs (single and `--from` batch) in
`internal/pipeline` with state in `internal/vault` (`State.RunsByDay`, JSON `runs_by_day`, added by the
config task: date `YYYY-MM-DD` local -> medium -> count).

- Before any provider call of a run, after intake has determined every entry's medium: for each distinct
  medium of the run with `runs_per_day > 0`, if `RunsByDay[today][medium] >= runs_per_day` the whole run
  fails `errs.CapReached` (exit 2) with a message naming the medium and limit and hint "raise
  caps.by_medium.<medium>.runs_per_day or wait until tomorrow"; nothing is sent and nothing is written
  (no inbox file, no state change, no commit). Absent or 0 = unlimited.
- After the run, increment the counter once per medium that actually called a provider in this run, prune
  every date other than today, and save the state through the transaction (it is an internal file like the
  rest of `state.json`). A run that called no provider (e.g. all entries failed intake) does not count.
- `--dry-run` never increments the counter.
- Today is `Deps.Now()` in local time.

Tests `TestCapsRunsPerDay` (pipeline, fake provider): with `runs_per_day: 1` for `article` the first article
run succeeds and increments the counter; the second the same day fails `CAP_REACHED`, the fake provider
records zero calls and the vault tree is byte-identical; a `poem` run is unaffected; the next day (moved
`Now`) succeeds again and old dates are pruned; a batch with one article and one poem entry is refused as a
whole when article is capped.

## Verification
`.harness/verify/v2/T013.sh` exits 0. It runs `TestCapsRunsPerDay` and the pipeline and vault packages, and
checks that `runs_by_day` is the state key and `CAP_REACHED` is used in the pipeline code.
