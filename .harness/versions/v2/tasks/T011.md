# T011: Batch add --from

Phase 3 · Model: opus: restructures the add orchestration into one run and one commit (data loss, idempotency) · Depends-on: T007 T010 · Covers: R30, R7 (batch)

## Brief
Add `slowhunch add --from <batch.txt>` (`internal/cli/cmd_add.go`, `internal/pipeline/`, new
`internal/pipeline/batch.go`).

Batch file format, one entry per line: `<file>` or `<file>|<url>|<title>|<author>` (exactly 0 or 3 `|`
separators; empty fields allowed). Blank lines and lines starting with `#` are ignored. Relative paths are
resolved against the batch file's directory. More than 50 entries -> `TOO_LONG` before any provider call
and nothing written. A line with another number of separators fails that entry with `BAD_INPUT`. `--from`
cannot be combined with a positional argument (`BAD_INPUT`). `--as`, `--note`, `--hunch` and `-force` apply to
every entry; `--url/--title/--author` flags are not allowed with `--from` (`BAD_INPUT`).

Run semantics:
- One run id for the whole batch, one transaction, one commit at the end (subject per the v1 commit format
  with command `add`), same crash-resume rules as a single `add`.
- Stage 1, per entry in order: intake (incl. `.pdf` via `Options.PDFCommand`), checks, secret check, gate.
  Stage 2, per entry that passed the gate: extract, place, write. Keep the list of gate-rejected entries in
  entry order on the batch state (the wildcard task builds on it).
- Entries fail independently: a failure (any code) becomes `{item: "line <n>: <file>", code, reason}` in the
  run's `errors`, n = 1-based line number in the batch file; every other entry is still written.
- Each entry gets its own v1-shaped report saved as `.slowhunch/reports/<run-id>-<n>.json` (n = 1-based entry
  index). The batch result printed on stdout is `{run_id, items: [<entry report>...], counts, git}` where
  `counts` sums the entries' counts plus `entries`, `written`, `failed`, and `git` is the one commit.
- Exit code: 0 when at least one entry was written; when all entries failed, the exit code of the first
  error.
- A single `add` (no `--from`) keeps its v1 behaviour and output byte for byte; refactor `Add` into reusable
  stage functions rather than duplicating it.

Tests `TestBatchAdd` (cli, fake model helper): 3 good `.txt` entries, 1 `.pdf` entry with a failing
`pdf.command`, 1 oversize entry -> 3 sources written, 2 errors naming line numbers, exactly one new commit,
5 entry report files. `TestBatchTooLong`: 51 entries -> `TOO_LONG`, no provider call, no commit, no file.
`TestBatchLineFormat`: comments/blank lines skipped, a line with 2 separators fails `BAD_INPUT` alone,
relative path resolution, all-failed batch exits non-zero.
