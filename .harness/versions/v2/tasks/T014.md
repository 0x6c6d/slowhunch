# T014: Per-medium cap tokens_per_run

Phase 3 · Model: sonnet: a token meter checked before provider calls · Depends-on: T002 T011 · Covers: R33, R23

## Brief
Implement `caps.by_medium.<medium>.tokens_per_run` in `internal/pipeline` for `add` runs (single and batch).

- Keep a run-wide token meter (tokens in + out of every provider call of the run, all roles).
- Before each provider call for an entry of medium M with `tokens_per_run > 0`: if the meter is already
  `>= tokens_per_run`, make no more calls for that entry; the call in flight always finishes.
- An entry that cannot finish (any of its gate/extract/place calls refused) is not written at all (no
  partial atoms, no source, no inbox file for it) and gets an `errors` entry with code `CAP_REACHED`
  ("line <n>: <file>" as item for batch entries, the source id for a single add). Entries already finished
  are written and committed normally; the run exits 0 when at least one entry was written.
- A single `add` refused before its first call fails `CAP_REACHED` (exit 2) with nothing written.
- Absent or 0 = unlimited; other media are unaffected by M's limit but share the run's meter.

Tests `TestCapsTokensPerRun` (pipeline or cli, fake provider whose replies report fixed token usage): a
batch of 4 article entries with a limit reached during entry 2 writes entries 1 and 2, marks 3 and 4
`CAP_REACHED` in `errors`, makes no provider call for 3 and 4, and makes one commit; a poem entry in the same
batch with no limit is still processed; limit 0 processes everything.
